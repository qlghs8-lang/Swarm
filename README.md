## 설계 목표 — "무리를 뚫고 나가는 감각"

이 프로젝트의 모든 구조적 결정은 하나의 목표에서 나왔습니다.
**적 무리는 피해 다니는 장애물이 아니라 밀고 뚫고 나가는 대상이어야 한다.**

그래서 다음 세 가지가 강제됩니다.

- 적이 **많아야** 한다 → 동시 400마리에서도 프레임이 흔들리지 않는 논-얼로케이션 설계
- 적이 **밀려야** 한다 → 넉백이 무리 전체로 전파되는 군중 물리
- 도망이 **영구 해법이 되면 안 된다** → 반지름 70의 원형 아레나 경계

아래 구현들은 전부 이 세 문장의 결과입니다.

## 핵심 구현

### 1. 무기 확장 구조 — 18종의 무기를 공통 프레임워크 하나로

캐릭터 3종이 각자 전용 무기 3개를 갖고, 그 9개가 전부 레벨 8에서 다른 무기로 진화합니다.
무기 종류가 18개까지 늘어나는 동안 **레벨업 카드·상점·UI 코드는 한 줄도 바뀌지 않았습니다.**

```csharp
public abstract class LevelableWeapon : MonoBehaviour, ILevelableWeapon
{
    [SerializeField] private int   maxLevel = 8;
    [SerializeField] private float damagePerLevel = 0.15f;
    [SerializeField] private float cooldownReductionPerLevel = 0.08f;
    [SerializeField] private LevelableWeapon evolutionTarget;

    public bool IsAvailable { get; private set; }   // 이번 판 카드 풀에 등장 가능한가

    protected float DamageMultiplier   => 1f + damagePerLevel * Mathf.Max(0, Level - 1);
    protected float CooldownMultiplier => Mathf.Max(0.3f, 1f - cooldownReductionPerLevel * Mathf.Max(0, Level - 1));

    public void Retire() { SetAvailable(false); enabled = false; }  // 진화 시 원본 비활성화
}
```

**왜 이렇게 했는가**

- `IsAvailable` 플래그를 무기 자신이 들고 있게 한 이유 — 카드 매니저가 "지금 캐릭터가 뭐지"를 몰라도 됩니다. `CharacterDefinition`이 캐릭터 적용 시점에 해당 캐릭터 무기만 `SetAvailable(true)`로 켜고, 카드 매니저는 켜진 것만 추첨합니다. 캐릭터를 추가해도 카드 로직은 그대로입니다.
- **데미지 없는 유틸리티 무기(대시, 힐)도 같은 클래스를 상속**합니다. 레벨업이 쿨타임 감소로만 작동할 뿐, 카드 UI 입장에선 다른 무기와 구별할 이유가 없습니다. 예외를 만들지 않는 쪽이 카드 매니저를 단순하게 유지합니다.
- 진화를 별도 시스템이 아니라 `evolutionTarget` 참조 + `Retire()` 두 개로 처리한 이유 — 진화 무기 역시 `LevelableWeapon`이므로 진화 후에도 레벨링·카드·UI가 그대로 작동합니다. 진화 전용 코드 경로를 만들면 9종 × 2배의 분기가 생깁니다.

### 2. 진화 전후로 끊기지 않는 액티브 스킬 UI

궁수의 대시는 진화하면 맹독 대시가 됩니다. 회피 버튼과 쿨타임 게이지는 **지금 어느 쪽이 활성인지 몰라야** 합니다.

```csharp
public interface IActiveRoll
{
    int   Level { get; }
    float CooldownProgress01 { get; }
    float CooldownRemaining  { get; }
    void  TryRoll();
}
```

**왜 이렇게 했는가** — UI가 `ArcherRollWeapon`을 직접 참조하면 진화 순간 참조가 죽은 무기를 가리킵니다.
`RollCooldownUI`는 인터페이스만 알고, 활성화된 구현을 찾아 씁니다. 그래서 진화 프레임에 버튼이 깜빡이거나 게이지가 리셋되지 않습니다. 세 번째 액티브 스킬을 추가해도 UI는 그대로입니다.

### 3. 군중 물리 — 밀림이 무리 전체로 전파되게

<!-- gif-06-knockback.gif  8초 — 넉백이 뒷줄까지 전파되는 장면. 슬로우면 더 좋음 -->

![넉백 전파](docs/media/gif-06-knockback.gif)

- **피격 판정을 물리 바디에서 분리** (`PlayerHurtbox`) — 플레이어 바디 콜라이더는 적을 물리적으로 밀어내는 역할(0.25), 피격 판정은 별도 트리거. 하나로 겸하면 밀어내기 반경을 조정할 때마다 "얼마나 맞는가"가 조용히 함께 바뀝니다.
- **넉백 중에는 추적 조향을 정지** — 밀려나는 힘과 플레이어를 향한 조향이 상쇄되어 제자리에서 떠는 현상을 막습니다.
- **하드 CC와 소프트 CC의 합산 규칙을 다르게** 설계:

```csharp
// 스턴: 긴 쪽이 이긴다. 짧은 프록이 긴 스턴을 끊어먹지 않도록.
public void ApplyStun(float duration)
    => _stunTimer = Mathf.Max(_stunTimer, duration);

// 둔화: 가장 강한 것 하나만. 재적용은 지속시간만 갱신.
// 곱연산으로 쌓이면 연쇄형 무기 하나가 무리 전체를 정지시킨다.
public void ApplySlow(float multiplier, float duration)
{
    _slowMultiplier = _slowTimer > 0f ? Mathf.Min(_slowMultiplier, multiplier) : multiplier;
    _slowTimer      = Mathf.Max(_slowTimer, duration);
}
```

**왜 이렇게 했는가** — 상태이상 합산은 "일반적인 규칙 하나"로 처리하고 싶은 유혹이 크지만, 스턴과 둔화는 성격이 다릅니다. 스턴은 켜짐/꺼짐이라 최댓값이 자연스럽고, 둔화는 배율이라 곱연산이 자연스러워 보입니다. 그런데 곱연산을 허용하면 아이스 볼트(연쇄 둔화) 하나로 무리 전체가 멈춰서 이 게임의 전제("뚫고 나간다")가 무너집니다. **규칙의 일관성보다 게임 감각을 지키는 쪽을 택했습니다.**

- 보스는 `EnemyStatusImmunity`로 넉백·스턴에 면역입니다. 매 타격마다 밀리면 슬램 윈드업을 끝내지 못해 보스전이 "제자리에서 사격 홀드"로 무너지기 때문입니다. 반면 둔화·도트·방어 감소는 그대로 들어가서 해당 빌드는 계속 유효합니다.

### 4. 보스 패턴 스케줄링 — 두 패턴이 같은 프레임에 겹치지 않게

- 슬램·운석은 각자 독립 타이머로 돌지만, 발동 직전 `BossPatternGate`(`IBossPattern.IsCasting`)를 거칩니다.
- 경고 원은 `BossTelegraph`가 공통으로 그리며, **실제 `Physics2D` 판정 반경과 정확히 같은 도형**입니다.

**왜 이렇게 했는가** — 패턴이 독립 타이머로 돌면 언젠가 반드시 같은 프레임에 겹칩니다. 그 순간 플레이어는 자기 잘못 없이 두 개의 경고 원을 동시에 피해야 하고, 이건 난이도가 아니라 불공정으로 읽힙니다. 게이트를 패턴 바깥에 두면 **패턴을 추가할 때 기존 패턴을 수정할 필요가 없습니다.**

### 5. 데미지 파이프라인 — 크리티컬을 무기 쪽에서 끝낸 이유

```
── 무기 쪽 (공격 1회) ──────────────────────────────────
statMul   = 1 + (주능력치가 공격력이면 AttackPower, 아니면 MagicPower)
isCrit    = Random.value < Clamp01(Luck)          // 공격 1회당 한 번만 굴림
damageMul = 무기레벨배율 × statMul × (isCrit ? 2.0 : 1.0)
damage    = Round(무기 기본데미지 × damageMul)

── 적 쪽 (EnemyHealth.ApplyDamage) ─────────────────────
def   = 방어력 − 임시 방어감소 − 관통력
final = Round(damage × (1 − Clamp(def, 0, 0.9)))
```

**왜 이렇게 했는가**

- **크리티컬은 무기 쪽에서 계산이 끝납니다.** `EnemyHealth`가 받는 `isCritical`은 순수하게 표시용(금색·확대)이고 계산에 관여하지 않습니다. 배율은 이미 `damage`에 녹아 있습니다. 덕분에 **적은 크리티컬이라는 개념을 몰라도 됩니다.**
- **굴림은 대상마다가 아니라 공격 1회당 한 번**입니다. 대상마다 굴리면 광역기가 터졌을 때 금색과 흰색 숫자가 뒤섞여 흩어지는데, 한 번만 굴리면 "한 방 크게 들어갔다"로 읽힙니다.
- **도트 틱과 고정 데미지 프록(흡혈·레이지)은 굴림 자체를 하지 않습니다.** 적 쪽에서 걸러내는 게 아니라 무기 쪽에서 `RollDamageMultiplier()` 대신 `BaseDamageMultiplier`를 읽습니다. 이 선택이 잠재 버그도 함께 막았는데 — 흡혈·레이지는 *다른 무기의 공격 도중에* 발동하므로, 여기서 굴리면 부모 공격이 아직 읽어야 할 `LastAttackWasCritical`을 덮어써 부모의 크리 표시가 프록 결과로 바뀝니다.
- **관통력은 내부적으로 물리/마법 두 스탯이지만 카드와 상점에는 하나만 노출**합니다. 캐릭터마다 주 능력치가 정해져 있어 어차피 한쪽만 읽히므로, 둘로 보여주면 플레이어는 절반의 확률로 자기에게 무의미한 선택지를 보게 됩니다. 안 쓰는 쪽을 함께 올리는 비용은 float 하나입니다.

### 6. 지속 효과의 소유권 — 장판이 아니라 적이 상태를 든다

독 장판은 지속 3초·쿨 4초지만 쿨감이 붙으면 쿨이 0.5초까지 내려갑니다. 제자리에서 대시를 반복하면 같은 자리에 장판이 4~6개 겹칩니다.

**장판이 각자 데미지를 넣는 흔한 구조였다면** 적 한 마리가 겹친 수만큼 틱을 맞아 DPS가 그대로 N배가 됩니다. 쿨감 스택이 곧 딜 곱연산이 되므로, 값을 조정해서 막을 수 있는 종류가 아닙니다. **상태(중독)는 적 한 명당 하나인데 그 상태를 굴리는 주체가 여럿이라는 소유권 불일치**가 본질입니다.

**대안과 선택**

1. 장판이 틱을 넣고 적이 중복 방지 플래그를 든다 → 플래그를 내리는 주체가 모호합니다. 첫 장판이 사라질 때 내리면 남은 장판이 있는데도 딜이 끊기고, 안 내리면 영구 면역이 됩니다
2. 적이 상태를 리스트로 들고 매 프레임 가장 센 것 하나만 적용 → 정확하지만 우선순위 규칙과 리스트 수명 관리가 새로 필요합니다
3. **장판은 신호만 보내고, 적이 상태 1개 + 타이머 1개만 유지한다** ← 선택

`PoisonGasCloud.Update()`는 범위 내 적을 훑어 `EnemyHealth.ApplyPoison()`을 부를 뿐 데미지를 직접 넣지 않습니다. `EnemyHealth`는 상태 / 타이머 / *이번 프레임에 신호가 왔는가* 세 필드만 들고, 자기 `Update()`에서 **타이머를 프레임당 정확히 한 번만** 감소시킵니다. 장판이 몇 개 겹쳐 몇 번을 호출하든 틱은 1회입니다.

**핵심은 지속시간 갱신 규칙을 정하지 않았다는 것입니다.** "연장할지 덮어쓸지"를 고민하는 대신 **장판 안에 있는 동안만 중독**이라는 상주 판정으로 바꿨고, 그래서 갱신 규칙 논쟁 자체가 사라졌습니다. 신호가 끊긴 다음 프레임에 상태를 내리고 방어 감소와 둔화를 원복합니다.

**대가로 받아들인 것**

- **last-write-wins**: 값이 다른 장판이 겹치면 그 프레임의 마지막 호출자 값으로 통일됩니다. "가장 센 장판이 이긴다"가 아니라 "마지막 장판이 이긴다"이므로, **장판 종류가 늘면 2안(매 프레임 최댓값)으로 옮겨야 합니다.** 지금은 종류가 하나라 드러나지 않습니다
- 틱은 중복되지 않지만 **순회는 중복**됩니다 — 장판이 겹친 수 × 범위 내 적 수만큼 Overlap이 돕니다
- 신호 세팅과 소비가 서로 다른 `Update()`에 있어 스크립트 실행 순서에 따라 최대 1프레임 지연될 수 있습니다

여기서 실제로 한 번 어긋났던 곳이 있습니다. 초기 구현은 디버프를 최초 진입에서만 걸어 **데미지는 갱신되는데 방어 감소·둔화는 첫 장판 값에 고정**됐고, 대입만 되고 읽히지 않는 죽은 필드가 그 흔적으로 남아 있었습니다. `RefreshPoisonDebuffs()`를 매 호출 끝에서 부르도록 고쳐 두 규칙을 맞췄고, 값이 실제로 바뀔 때만 세터를 타도록 캐시를 둬 겹친 수만큼 세터가 호출되는 것을 막았습니다.

**남은 부채** — 화상은 같은 문제를 다른 규칙으로 풀고 있습니다. `FirePatch`는 `HashSet`으로 장판당 한 번만 점화하고 `ApplyBurn`이 지속시간을 연장합니다. 독은 상주형, 화상은 지속시간 연장형입니다. 설계 의도가 아니라 두 무기를 따로 만들다 갈린 것이고, 같은 문제에 규칙이 두 벌 존재합니다. 통합한다면 상주형으로 모으는 쪽이 맞습니다.

## 성능 최적화

이 게임은 동시 적 400마리 + 투사체 수십 개가 상시 유지됩니다.
**프레임당 GC 할당 0**을 목표로 타격 판정 전 경로를 재설계했습니다.

### 논-얼로케이션 타격 판정

`Physics2D.OverlapCircleAll`은 **호출할 때마다 새 배열을 할당**합니다. 초기 구현은 모든 무기가 매 타격 틱마다 이걸 호출했고, 레이어 필터도 없어서 픽업·투사체·플레이어까지 전부 수집한 뒤 태그 검사로 버렸습니다.

```csharp
// EnemyTargeting — 레이어 필터 + 호출자 소유 버퍼로 전환
private static ContactFilter2D _enemyFilter;                   // 한 번만 구성
private static readonly List<Collider2D> QueryBuffer = new();   // 재사용, 재할당 없음
```

- 적 레이어로 필터링해 **수집량 자체를 줄이고**, 결과를 호출자가 소유한 `List`에 씁니다.
- 재진입 안전성을 구분해서 처리했습니다 — `FindNearest`는 반환 전에 버퍼를 완전히 소비하므로 공유 버퍼가 안전하지만, `FindMultiple`은 결과가 살아 있는 동안 호출자가 데미지를 넣고 그 과정에서 데미지 이벤트 핸들러가 다시 쿼리를 부를 수 있어 **호출자가 자기 리스트를 넘기게** 했습니다.
- 같은 패턴을 `ChasingBlade` / `FirePatch` / `MageBoltWeapon` / `ArcherFocusWeapon` 등 판정을 도는 모든 지점에 적용했습니다.

### 오브젝트 풀 — 세 개로 나뉜 이유

풀은 처음부터 셋이 아니었습니다. **필요가 생길 때마다 축이 하나씩 드러났습니다.**

| 클래스                | 담당                                                                       | 갈린 축               |
| --------------------- | -------------------------------------------------------------------------- | --------------------- |
| `ObjectPool`        | 한 컴포넌트가 자기 프리팹을 독점 생성 (무기→투사체, 스포너→적)           | — (기본)             |
| `SharedObjectPool`  | 여러 소유자가 같은 프리팹을 생성 (적 수백이 각자 데미지 숫자·픽업을 떨굼) | **소유권**      |
| `RuntimeObjectPool` | 프리팹이 없고 코드로 조립되는 이펙트 (낙뢰 볼트, 운석, 화염 장판, 독 구름) | **프리팹 유무** |

**왜 통합하지 않았는가**

- **소유권**: 무기는 자기 투사체의 유일한 생성자라 인스턴스 필드로 풀을 들면 됩니다. 데미지 숫자는 다릅니다 — 적 하나하나가 생성자라, 컴포넌트마다 풀을 두면 **적 400마리에 풀 400개**가 생깁니다. 그래서 후자는 프리팹을 키로 하는 정적 딕셔너리입니다. 다만 `SharedObjectPool`은 `ObjectPool`을 버리지 않고 값으로 감쌉니다 — 중복 구현이 아니라 소유권 계층이 하나 얹힌 구조입니다.
- **생성 계약**: 앞의 둘은 `GameObject prefab`을 받아 `Instantiate`합니다. 낙뢰 볼트·운석은 복제할 원본이 없어 `new GameObject` + `AddComponent`로 조립되므로 **`Func<GameObject>` 팩토리**를 받습니다. 파라미터가 다른 게 아니라 계약 자체가 다릅니다.
- 팩토리로 통일해 하나로 합칠 수는 있지만, 그러면 (a) 씬 언로드 시 `Pools.Clear()`가 필요한 정적 공유와 무기와 함께 죽는 인스턴스 소유가 한 타입에 섞이고, (b) 콜라이더를 가진 오브젝트에만 필요한 `Rigidbody2D.position` 동기화가 순수 시각 이펙트에까지 걸리며, (c) 프리팹 참조가 곧 정체성인 딕셔너리 키가 사라집니다.

> `RuntimeObjectPool`은 성능 문제를 고친 것이 아닙니다. 이 넷은 생성 빈도가 초당 1회 미만이라 실측상 프레임에 부담이 되지 않았습니다. 문제는 **프리팹이 없다는 이유만으로 이 넷만 규칙에서 빠져 있다**는 상태 자체였습니다 — 발사 빈도나 장판 지속시간을 밸런싱할 때마다 성능을 다시 확인해야 합니다. 예외를 없애는 비용이 파일 하나였으므로, 매번 확인하는 비용보다 싸다고 판단했습니다.

### 측정 — 에디터 수치를 믿지 않기까지

에디터에서 처음 잰 값은 **프레임당 약 9,000 B**였습니다. 그것이 게임의 할당이 아님을 확인하는 데 세 단계가 걸렸습니다.

**① 스케일링이 말이 되지 않았습니다.** 적을 150 → 701마리로 **4.7배** 늘렸는데 GC는 9,953 → 10,087 B로 **1.3%** 움직였습니다. 최소자승으로 분해하면 고정분 ≈ 9,921 B + 적 1마리당 ≈ 0.26 B. **게임 내용이 4.7배로 바뀌었는데 따라 움직이지 않는 비용은 게임의 비용이 아닙니다.**

**② Profiler로 소재를 특정했습니다.** Hierarchy를 GC Alloc으로 정렬하니 `EditorLoop` 296 B는 전량이 `PackageManager` / `Rendering` / `Wwise Editor` — 셋 다 `UnityEditor` 네임스페이스라 빌드에 존재하지 않는 코드였고, `PlayerLoop` 368 B는 전량이 `GUIUtility.BeginGUI`, 즉 디버그 오버레이의 `OnGUI` 하나였습니다. 각 총합과 하위 분기 값이 일치했으므로 **나머지 가지는 전부 0 B** — `EnemyHealth.Update` ×400, `EnemyChaser.FixedUpdate` ×400, 무기 타겟팅, 데미지 숫자가 모두 0이었습니다.

**③ 빌드가 확인했습니다.** 400마리 기준 9,000 B → **3 B**.

**에디터 수치를 그대로 적었다면 3,000배 틀린 숫자를 쓸 뻔했습니다.**

![프레임당 GC 할당의 소재 특정 — Unity Profiler](docs/media/img-02-profiler.png)

*Play Mode, GC Alloc 내림차순. `PlayerLoop` 총 368 B가 `GUIUtility.BeginGUI()` 한 갈래에 전부 들어가 있으므로 **나머지 가지의 합은 0 B**입니다 — 적 400마리가 돌고 있는 프레임에서 게임 코드의 할당은 0입니다. `EditorLoop` 296 B는 전량 `UnityEditor` 네임스페이스라 빌드에 존재하지 않습니다.*

### 측정 도구가 자기가 재는 값을 왜곡한 사례

측정은 `DebugPerfProbe`를 직접 만들어 자동화했는데, **가장 많이 고친 것은 게임이 아니라 도구 자신**이었습니다. 총 8건 중 셋:

- **`MethodInfo.Invoke`가 측정 창 안에서 할당했습니다.** 죽은 적을 채우는 경로가 호출마다 인자를 박싱하고 있었습니다 → `Delegate.CreateDelegate`로 바인딩해 0으로
- **GC 적합이 타임스텝 클램프 구간에 오염됐습니다.** 한 프레임이 물리 스텝 16회를 담고 있으면 "프레임당" 수치가 16배로 부풀려집니다. 그 행을 포함해 적합했더니 판정이 "게임플레이 할당 있음"으로 뒤집혔습니다 → 클램프 구간 자동 제외
- **디버그 오버레이의 `OnGUI`가 측정을 오염시켰습니다.** 측정하려는 값과 같은 자릿수의 할당원이었습니다 → 측정 창 동안 자동으로 끄도록

**계측기가 측정 대상에 기여하지 않는지 확인하는 것이 측정의 일부**라는 것을 여기서 배웠습니다.

### 측정에서 부수적으로 나온 관찰

- **물리 타임스텝의 절벽** — 프레임 시간이 `fixedDeltaTime`(20 ms)을 넘으면 한 프레임에 물리 스텝이 여러 번 돌고, 스텝 하나가 20 ms를 넘으면 엔진이 `Maximum Allowed Timestep`(333 ms)까지 몰아 돌립니다. 에디터 2,200마리 측정에서 프레임 시간이 **341 ms**로 나왔는데 그 상한값과 거의 정확히 같습니다. 프레임 비용은 연속적으로 늘지 않고 계단처럼 튑니다
- **GC 수집과 최저 FPS는 같은 문제였습니다** — 에디터 15회차를 GC 수집 여부로 나누면 최저 FPS가 완전히 분리됐습니다. 수집 있음 5건 37~59 FPS / 없음 10건 61~197 FPS로 겹치는 구간이 없고, 수집 1회가 약 22 ms 스파이크를 만듭니다

## 트러블슈팅

### 화면 밖으로 처진 적을 삭제하지 않고 재배치한 이유

**증상** — 적 밀도를 올리자 생존 적 수가 수렴하지 않고 계속 증가했습니다. 탱커의 이동속도는 1, 플레이어는 4라서 한 방향으로 달리면 느린 적은 영원히 따라잡지 못하고 뒤에 쌓이기만 했습니다. 프레임이 흔들렸고, 난이도를 측정하는 것 자체가 불가능해졌습니다.

**원인** — 적을 제거하는 경로가 "죽이는 것" 하나뿐이었습니다. 스폰 속도를 올리면 생존 수가 발산합니다.

**대안**

1. 멀어진 적을 파괴 → GC 스파이크 + 그 적이 보유한 경험치/골드 드랍이 통째로 소멸
2. 풀에 반납 후 재스폰 → GC는 해결되지만 드랍 유실과 "압박이 끊기는" 문제는 남음
3. 인스턴스를 유지한 채 좌표만 플레이어 주변으로 이동

**선택** — 3번. 22유닛 밖으로 처진 적을 0.5초 주기로 스윕해 플레이어 주변으로 재배치합니다. 거리가 충분해 시야에서 순간이동이 보이지 않고, 적이 들고 있던 경험치 배율도 그대로 유지됩니다. 동시에 `maxActiveEnemies` 상한으로 물리 비용의 최악값을 고정했습니다.

**결과** — 초기 상한은 150이었습니다. 측정해 보니 150마리가 **0.84 ms/frame**, 상한을 400으로 올려도 **1.41 ms/frame**으로 60 FPS 예산의 8.5%였습니다. **상한이 성능 병목이 아니라 난이도 곡선을 인위적으로 자르고 있었다**는 뜻이라, 400으로 올려 필드가 실제 평형점에 도달하게 했습니다. 같은 측정에서 1,600마리까지도 85 FPS가 나왔으므로 상한은 여전히 성능이 아니라 게임 디자인이 정하는 값입니다.

### 플레이어를 "항상 위"로 올리지 않고 적과 같은 레이어에 둔 이유

**증상** — 적이 뭉치는 구간에서 겹친 스프라이트의 앞뒤가 프레임마다 뒤바뀌었고, 플레이어가 무리에 파묻혀 자기 위치를 놓치는 일이 생겼습니다. 새 이펙트를 만들 때마다 "이건 몇 번이더라"를 찾아야 했습니다.

**원인** — Sorting Layer가 `Default` 하나뿐이라 그리기 순서를 전부 `sortingOrder` 숫자 하나로 구분하고 있었습니다. 아레나는 -100~-60, 이펙트는 1~2, 데미지 숫자는 10을 쓰는데 **플레이어·적·픽업·투사체는 전부 0에 방치**되어, 이 그룹의 앞뒤는 Unity의 tie-break에 맡겨진 상태였습니다. Transparency Sort Mode도 기본값(z축)인데 게임플레이 오브젝트는 전부 z=0이라 정렬 기준이 사실상 없었습니다.

**대안**

1. 레이어 없이 `sortingOrder` 규약만 문서화 → 매직 넘버가 그대로 남고, 바닥까지 휩쓸리므로 Y축 정렬을 켤 수 없음
2. 레이어 분리 + **플레이어를 적보다 위 레이어에 고정** → 플레이어가 절대 안 가려짐
3. 레이어 분리 + 플레이어와 적을 한 레이어(`Character`)에 두고 커스텀 정렬 축 `(0,1,0)`으로 정렬

**선택** — 2번으로 갔다가 되돌려 3번으로 갔습니다. 플레이어의 몸통 콜라이더 반지름은 0.20인데 스프라이트 폭은 0.56입니다(히트박스를 스프라이트보다 작게 만들려고 몸통을 0.5 → 0.25로 줄인 결과 — `PlayerHurtbox`). 즉 **적이 플레이어 스프라이트 안쪽까지 들어오는 것은 이미 확정된 조건**이고, 이 상태에서 플레이어를 위 레이어에 두면 바로 앞에 선 적이 플레이어 뒤로 숨어 깊이가 거꾸로 읽혔습니다. 콜라이더를 키워 겹침 자체를 없애는 안도 검토했지만, 몸이 닿는 거리와 피해를 받는 거리는 물리적으로 분리할 수 없어 난이도 상승을 동반합니다. 겹침이 불가피하다면 겹칠 때 자연스러운 쪽을 택하는 편이 낫다고 판단했습니다.

**결과** — 레이어 9종(`Ground → Decal → Prop → Wall → Pickup → Character → Effect → Overlay`)과 Y축 정렬로 전환했습니다. `Default`에 남은 렌더러는 0개, `sortingOrder`는 같은 레이어 안의 예외에만 씁니다(예: `Decal`의 마모 띠 0 → 중앙 문양 1 → 화염 장판 2 → 슬램 경고 3). 레이어 이름은 `SortingLayers` 상수로 모아, 이후 추가한 렌더러(보스 낙석·슬램 이펙트, 항아리)는 숫자를 고르지 않고 레이어만 고르면 됩니다. 렌더링만 바꾼 변경이라 콜라이더·히트박스 수치는 그대로입니다.

### 배속에서만 드러난 hit-history 메모리 릭

**증상** — 공전검·소드 체이싱을 든 상태로 F1 배속(10배)을 걸면 판이 길어질수록 프레임이 완만하게 밀렸습니다. 일반 속도 플레이에서는 체감되지 않아 오래 눈에 띄지 않았습니다. 배속에서는 10분치 누적이 1분에 일어나므로 릭이 먼저 드러납니다.

**원인** — 두 무기는 같은 적을 연타하지 않으려고 `Dictionary<Collider2D, float>`에 마지막 타격 시각을 기록합니다. 그런데 적은 오브젝트 풀로 재사용되고, **이 테이블에서 항목을 제거하는 코드가 어디에도 없었습니다.** 쿨다운이 지나 다시는 조회에 쓰이지 않을 항목까지 전부 남아 한 판에 수천 개가 쌓였고, 파괴된 오브젝트를 붙잡은 채 딕셔너리 조회를 함께 느리게 만들었습니다. **풀링과 "대상을 키로 쓴 컬렉션"이 만나면 생기는 전형적인 형태입니다.**

**대안**

1. 적이 풀에 반납될 때 자기를 참조하는 모든 테이블에 알린다 — 정확하지만 적이 무기를 역참조해야 해서 의존 방향이 뒤집힌다
2. 딕셔너리 대신 만료 시각만 담는 링버퍼 — 조회가 O(n)이 되고 무기당 상한을 정해야 한다
3. 주기적으로 만료 항목을 훑어 지운다

**선택** — 3번. **쿨다운이 지난 항목은 정의상 다시는 타격을 막을 수 없으므로, 지워도 동작이 바뀌지 않는다**는 점이 결정적이었습니다. 2초 주기로 훑으므로 최대 2초치만 남고 스윕 비용은 그 순간 살아 있는 항목 수에 비례합니다. 반납 시점 정리(1번)보다 정리가 늦는 대신 **무기가 적을 알 필요도, 적이 무기를 알 필요도 없습니다.** 주기 2초는 쿨다운(0.2~0.5초)보다 충분히 길어 스윕이 잦지 않고, 쿨다운보다 짧게 잡으면 아직 유효한 항목을 훑기만 하고 못 지우므로 낭비입니다.

**결과** — 테이블 크기가 판 길이에 비례해 증가하던 것에서 "최근 2초 안에 때린 적 수"에 비례하는 상수 수준으로 바뀌었고, 배속 장시간 플레이에서 프레임이 밀리는 현상이 사라졌습니다. 같은 패턴이 남아 있는지 "이미 때린 대상을 기억하는" 자료구조를 전수 조사했고, `Projectile`·`ChainLightningBolt`는 `Launch()`에서 초기화, 장판류의 판정 버퍼는 매 질의마다 덮어쓰므로 누적이 없었습니다. 다만 `FirePatch`가 점화 대상을 기억하는 `HashSet`은 같은 계열이라 풀 재사용 시 초기화가 필요했고, 실제로 그 처리를 추가한 이력이 남아 있습니다 — **풀링 + 대상을 키로 쓴 컬렉션**은 이 프로젝트에서 두 번 나온 패턴입니다.

> 이 릭은 프로파일링이 아니라 **코드를 읽다가** 발견했습니다. 배속에서만 체감되던 현상이 그 발견으로 설명됐습니다.

## 프로젝트 구조

```
Assets/_Project/
├── Scripts/
│   ├── Player/     이동, 체력/피격(PlayerHurtbox로 판정 분리), 경험치·레벨, 스탯
│   ├── Enemy/      추적 AI, 군중 물리(넉백/스턴/둔화), 보스 패턴 2종 + 공통 경고 + 게이트
│   ├── Weapon/     LevelableWeapon 상속 무기 18종, 오브젝트 풀, 논-얼로케이션 타겟팅
│   ├── LevelUp/    런 패시브(전략 패턴), 가중치 기반 카드 추첨
│   ├── Spawner/    난이도 곡선, 대규모 웨이브, 보스 스폰, 적 리사이클
│   ├── Arena/      원형 경계, 지형 시드 고정 생성, 항아리 배치
│   ├── Game/       캐릭터 정의, 게임 흐름, 픽업/상점/타이틀
│   ├── UI/         HUD, 결과 연출, 보스 체력바, 버프 아이콘, 가상 조이스틱
│   ├── Audio/      Wwise 라우팅(AudioDirector)
│   ├── Rendering/  Sorting Layer 상수
│   └── Debug/      개발 전용 도구 (출시 시 폴더째 삭제 가능하도록 격리)
├── Data/           무기·패시브·캐릭터 ScriptableObject
├── Textures/       전량 자체 제작 스프라이트 (.aseprite 원본 포함)
└── Scenes/         Title / Game / TestStage
```

아레나 지형·항아리·설정 스킨은 `Resources/`에서 이름으로 로드합니다. `ArenaBuilder`와 `PotScatterer`는 `[RuntimeInitializeOnLoadMethod]`로 스스로 설치되는 정적 클래스라 인스펙터가 없고, 직접 참조를 쓰면 **`Game.unity`와 `TestStage.unity` 두 씬에 같은 배선을 중복으로 유지**해야 합니다. 아트를 한 장 추가할 때마다 씬 두 개를 열어야 하고, 하나를 빠뜨리면 테스트 스테이지에서만 지형이 달라집니다. Resources는 폴더에 넣는 것으로 배선이 끝납니다.

Resources가 안티패턴이 되는 조건은 "쓰지 않는 에셋까지 강제로 상주한다"인데, 여기 있는 15장은 전부 아레나가 존재하는 내내 쓰입니다(총 140KB). Addressables로 옮겨도 똑같이 메모리에 있고, 얻는 것(선택적 로드·원격 배포)은 단일 씬 게임에서 필요가 없습니다. 스테이지별 타일셋처럼 "동시에 하나만 쓰는" 에셋이 생기면 그때가 옮길 시점이고, 전환 비용은 `Resources.Load` 호출 4곳입니다.

`Scripts/Debug/`는 F1 10배속, F2 보스 즉시 소환, 강제 레벨업/진화, 스탯 오버레이 등 테스트 도구를 한 폴더에 격리해 두었습니다. 전부 에디터·개발 빌드에서만 동작합니다.
