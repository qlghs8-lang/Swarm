# Swarm 아트 제작 계획

아트는 전부 직접 제작하며, 무료 에셋 스토어를 포함한 외부 에셋은 사용하지 않는다. 제작 파이프라인은 카테고리에 따라 세 가지로 나뉜다.

- **플레이어 캐릭터 / 적**: PixelLab로 생성 → Aseprite 후가공 (2장 참고)
- **무기 이펙트**: GPT·Gemini로 레퍼런스 이미지 생성 → Aseprite에서 선 정리 후가공 (3장 참고)
- **UI / 타일 / 픽업 오브젝트**: aseprite-mcp로 Aseprite를 직접 조작해 생성 (4장 참고)

세 번째 방식은 앞의 두 가지와 성격이 다르다. 캐릭터와 이펙트는 "무엇이 그려져 있는가"가 핵심이므로 생성 AI의 이미지가 출발점이 되지만, UI 프레임·타일·픽업은 규격 자체가 결과물을 결정한다. 9-slice 보더가 정확히 6px이어야 하고, 타일은 이음매가 픽셀 단위로 맞아야 하며, 픽업은 실루엣으로 구분되어야 한다. 이러한 요소는 레퍼런스를 정리하는 방식보다 도형·팔레트·좌표를 직접 지정하는 방식이 더 빠르고 정확하다.

## 2. 캐릭터/적 파이프라인 (PixelLab + Aseprite)

1. PixelLab MCP `create_character`로 초안을 생성한다. 레퍼런스 이미지 없이 텍스트 설명만 사용하며 `mode="standard"`, `view="low top-down"`으로 지정한다(레퍼런스 이미지를 사용하면 원본의 앵글 편향이 반영되어 탑다운이 아닌 측면·카드아트 구도가 생성된다)
2. Idle은 `breathing-idle` 템플릿으로 먼저 시도하고, 무기·지팡이 등 소품이 일부 프레임에서 사라지면 `mode="v3"` 커스텀에 "계속 쥐고 있음"을 명시해 재생성한다
3. Walk는 템플릿 모드(`walking-4-frames` 등)에서 방향이 반전되어 뒷모습이 섞이는 문제가 발생할 수 있으므로, 처음부터 `mode="v3"` 커스텀에 "항상 정면 유지"를 명시해 생성한다
4. (필요시) 액티브 스킬 애니메이션(예: 대시)도 `mode="v3"` 커스텀으로 생성한다. 무릎 굽힘, 상체 기울기 등 동작을 구체적으로 기술해야 의도한 실루엣을 얻을 수 있다
5. Aseprite에서 태그별(`Idle`, `Walk`, `Roll` 등)로 프레임을 정리한 뒤 `.aseprite`로 저장한다(Aseprite CLI의 `-b --script` 옵션으로 스크립트 조립이 가능하다)
6. Unity `com.unity.2d.aseprite` 임포터로 임포트하고, `Generate Animation Clips`를 체크한 뒤(기본값) Pixels Per Unit을 50으로 수정한다(Pivot Alignment는 최초 1회 Bottom Center로 설정하면 이후 신규 임포트에 프로젝트 기본값으로 자동 상속된다)
7. 전용 에디터 툴(`Assets/_Project/Scripts/Editor/<Character>AnimatorSetup.cs` 패턴)로 AnimatorController를 생성하고, Player의 두 씬(Game.unity, TestStage.unity)에 임시 연결해 확인한다
8. `CharacterDefinition`(`defaultSprite`/`animatorController` 필드)에 연결한다. `CharacterVisualLinker.cs`로 각 캐릭터 에셋(`Warrior.asset` 등)에 스프라이트와 컨트롤러를 배선한다. 이 작업을 거쳐야 타이틀에서 선택한 캐릭터가 실제로 표시된다(씬에 직접 배치만 하면 마지막으로 설정한 캐릭터만 표시된다)
9. Play 모드에서 캐릭터별로 선택해 플레이하며 루프와 전환을 확인하고, 어색한 프레임만 Aseprite에서 수정한다(전체 재작업은 지양한다)

### 캔버스/해상도

- 소스 해상도는 캐릭터 콘텐츠 기준 48px 내외로 한다. Vampire Survivors, Brotato 계열 장르에 적정한 크기이며, 16×16 및 24×24는 디테일이 뭉개져 부적합하다
- 렌더링 방식은 정면(south) 스프라이트 1개에 `SpriteRenderer.flipX`로 좌우만 전환한다. `PlayerController.cs`가 이미 이 방식이므로 8방향 회전 스프라이트는 필요하지 않다

### 주의 사항

- 스프라이트 pivot을 bottom으로 변경하면 `transform.position`이 발 아래 지점이 된다. 기존 Player의 `CircleCollider2D`는 `offset.y = 0.7`(가슴 높이)로 설정되어 있으므로, 무기 판정이나 픽업 자석과 같이 플레이어 기준 좌표가 필요한 코드는 `transform.position`이 아니라 `PlayerStats.AttackOrigin`(콜라이더의 실제 중심)을 사용해야 한다. 새 캐릭터를 추가할 때도 동일하게 확인한다.
- 템플릿 애니메이션(`walking-4-frames` 등)은 방향 일관성이 유지되지 않을 수 있다. 궁수 Walk에서 일부 프레임이 뒷모습으로 전환되는 문제가 발생했으며, `mode="v3"` 커스텀에 "항상 정면 유지"를 명시해 해결했다.
- 템플릿 애니메이션은 캐릭터가 든 소품(무기·지팡이)을 모든 프레임에서 유지하지 못할 수 있다. 마법사 Idle에서 지팡이가 1프레임에만 남고 나머지 프레임에서 사라졌으며, `mode="v3"` 커스텀에 "소품을 계속 쥐고 있음"을 명시해 해결했다.
- 8방향 회전 생성 시 일부 대각선 방향에서 무기가 두 개로 겹쳐 보이는 경우가 있다(예: 전사 검). south 1방향과 flipX만 사용하므로 실사용에는 영향이 없다.
- 씬에 Player 스프라이트·Animator를 직접 배치하는 것과 `CharacterDefinition` 연결은 별개의 작업이다. `<Character>AnimatorSetup.cs`의 `ApplyToScene()`은 에디터에서 확인하기 위한 임시 수단이며, 실제 게임에서 캐릭터별 외형이 전환되려면 `CharacterVisualLinker.cs`로 `CharacterDefinition` 에셋까지 배선해야 한다.

## 3. 이펙트 파이프라인 (GPT·Gemini 레퍼런스 → Aseprite 선 정리)

1. AI 이미지 생성 도구(GPT, Gemini 등)로 이펙트 레퍼런스 시트를 생성한다. 스타일·팔레트·프레임 구성(프레임 수, 동작 단계 등)을 구체적으로 명시한다
2. 레퍼런스 이미지를 Aseprite로 가져와 선과 도트를 정리한다(처음부터 수작업으로 트레이싱하는 방식은 품질이 확보되지 않아 채택하지 않았다. 레퍼런스를 활용하고 선과 색을 정리하는 방식으로 진행하며, 사용자가 직접 작업한다)
3. 프레임 스페이싱과 타이밍을 조절한다
4. Unity 연동과 인게임 테스트를 진행한다. `Swarm/Art Test/...` 메뉴 패턴의 Editor 링커 스크립트로 씬·프리팹에 배선한다

### 작업 시 참고 사항

- 캐릭터가 이미 들고 있는 무기·도구(활, 지팡이 등)는 이펙트에 포함하지 않는다. 캐릭터 스프라이트가 해당 무기를 들고 렌더링되므로, 이펙트에도 그리면 두 개로 겹쳐 보인다. 궤적·충격·빛 등 이펙트 요소만 그린다
- 레퍼런스가 에어브러시나 블러 느낌인 경우 기존 스타일(1px 외곽선 + 디더링 없는 면 분할)과 차이가 있을 수 있다. 재해석 방향은 선 정리 과정에서 판단하며, 이펙트 간 스타일이 완전히 통일될 필요는 없다
- 투사체 계열은 비행 중 스프라이트와 명중 시 히트 이펙트를 분리해 제작하는 편이 연동에 유리하다. 비행 프레임은 1~4장, 명중 이펙트는 짧은 버스트(1~2프레임)로 별도 제작한다. 발사 빈도가 높은 무기는 히트 이펙트를 생략하거나 짧고 작게 유지한다

### 프로젝트 기술 표준 (그림체와 무관하게 항상 적용)

- 캔버스 64×64px, PPU 50
- Sprite Mesh Type: Full Rect (Tight 아님) — 뾰족한 실루엣이 확대 시 깨지는 문제 방지
- Pivot Space: Canvas + Pivot Alignment: Center
- 스프라이트 원본은 정면 방향을 오른쪽(+X)으로 통일해 제작한다. 코드의 회전 공식(`Atan2(facing) → Euler`)이 오른쪽을 정면으로 가정하므로, 다른 방향으로 제작하면 무기별 회전 보정 상수를 추가해야 한다
- 이펙트의 크기와 위치는 실제 무기 판정 반경(`radius`)이나 스케일 필드에 비례하도록 코드에서 조정한다. 레벨업이나 범위 증가 패시브로 반경이 커질 때 이펙트도 함께 확대되어야 하며, 오프셋도 같은 배율로 스케일해야 캐릭터와 겹치지 않는다
- 순간적으로 발생하는 원샷 이펙트(타격 플래시, 슬래시 등)에는 Additive 블렌드(`SpriteAdditive.mat`)가 적합하고, 지속형 장판 이펙트(독 구름 등)는 알파 블렌드를 유지하는 편이 여러 개가 겹쳤을 때 과다 노출되지 않는다

### 주의 사항 (이펙트)

- 스프라이트시트의 프레임마다 트림 영역이 다르면 기본 상속 피벗(Bottom Center, 프레임별 trim 기준)이 프레임마다 다른 지점을 가리켜 회전 시 위치가 어긋난다. 이펙트처럼 프레임별 실루엣 변화가 큰 애니메이션은 Pivot Space를 Canvas로, Pivot Alignment를 Center로 명시적으로 지정해야 한다(캐릭터의 Bottom Center 상속값을 그대로 두지 않는다)
- Pivot Alignment를 Center로 변경해도 프레임별 피벗이 재계산되지 않는 경우가 있다. 적용 후에는 `.meta`의 `animatedSpriteImportData[].pivot` 값을 직접 확인해 Y가 0.5 부근인지 검증한다(x=1.8, y=-4처럼 0~1 범위를 크게 벗어나면 비정상이다). 값이 갱신되지 않으면 Inspector에서 Pivot Alignment를 다른 값으로 변경했다가 다시 Center로 지정하고 Apply해 변경 이벤트를 발생시킨다
- 색상 톤 선택에 주의한다. 짙은 남색 계열은 물 속성으로 인식되기 쉬우며, 밝은 파스텔 톤이 검기나 광 속성으로 더 무난하게 읽힌다
- 스프라이트 서브에셋은 내용이 변경되면 내부 식별자가 갱신되므로, `.aseprite`를 덮어쓸 때마다 연결 스크립트(`Swarm/Art Test/Link ...` 패턴)를 다시 실행해야 한다
- 바닥에 그리는 경고 원은 Sorting Layer를 `Decal`로 지정해야 한다. 이 프로젝트에서 기본 레이어는 `Ground`보다 아래에 있어, 지정하지 않으면 경고 원이 바닥 아래에 그려져 표시되지 않는다
- 패턴 아트가 탑다운이 아니라 3/4 원근으로 제작된 경우 경고 원도 같은 비율로 세로 압축해야 한다(`BossTelegraph`의 verticalSquash). 그렇지 않으면 경고 도형과 착탄 이펙트의 형태가 어긋난다
- 방향성이 있는 판정(부채꼴·원뿔 등)은 `AoeWeaponData.attackAngleDegrees`로, 캐릭터 앞쪽으로 오프셋된 판정(예: 넓은 범위 슬램)은 `forwardOffset`으로 표현할 수 있다. 360도 각도와 오프셋을 조합하면 캐릭터 주변 원형이 아니라 캐릭터 앞쪽에 위치한 원형 판정이 된다
- 스크립트로 동적 생성한 렌더러에 Additive 머티리얼을 처음 사용하면, 해당 셰이더 변종이 최초 사용 시점에 컴파일되면서 한 프레임 동안 색이 깨지는 플래시가 발생할 수 있다. 씬 로드 시 알파 0으로 한 프레임만 렌더링해 미리 컴파일하는 워밍업 코루틴으로 방지한다(기존 무기 스크립트의 `WarmUpEffectShader` 패턴 참고)

## 4. UI/타일/픽업 파이프라인 (aseprite-mcp)

레퍼런스 이미지 없이 aseprite-mcp로 Aseprite를 직접 조작해 생성한다. 도형·그라디언트·디더링·팔레트를 좌표로 지정하므로, 9-slice 보더나 타일 이음매처럼 픽셀 단위 정확도가 요구되는 요소를 수작업으로 맞출 필요가 없다.

1. 캔버스 크기와 팔레트를 먼저 결정한다. 이 값이 곧 규격이 된다(UI 48×48/PPU 100, 타일 32×32/PPU 32, 픽업 16×16/PPU 32)
2. 도형·그라디언트·디더링으로 작업한 뒤 PNG로 익스포트해 `Assets/_Project/Textures/<카테고리>/`에 배치한다
3. 임포트 설정은 Filter Mode를 Point로 지정하고 압축을 사용하지 않는다. 9-slice가 필요한 UI는 Sprite Border를 6px로 지정한다
4. Unity 배선을 진행한다. 씬·프리팹의 `m_Sprite`를 교체하고, 버튼 전환을 SpriteSwap으로 변경하며, 런타임 생성물은 코드에서 배치한다

### 카테고리별 규격

| 카테고리              | 캔버스   | PPU | 1스프라이트 크기 | 비고                                          |
| --------------------- | -------- | --- | ---------------- | --------------------------------------------- |
| UI 프레임/버튼        | 48×48   | 100 | — (9-slice)     | Sprite Border 6px. 바(Fill_HP/EXP)만 보더 4px |
| 바닥 타일·돌담·장식 | 32×32   | 32  | 1유닛            | 잔디는 이음매 없이 반복                       |
| 중앙 문양             | 256×256 | 32  | 8유닛            |                                               |
| 드랍 픽업             | 16×16   | 32  | 0.5유닛          | 프리팹 스케일 1                               |

### 작업 시 참고 사항 (적용 결과 효과가 확인된 항목)

- 대량으로 겹치는 오브젝트는 색이 아니라 실루엣으로 구분한다. 경험치는 마름모, 골드는 원으로 통일해 화면에 수십 개가 겹쳐도 종류가 구분된다. 색만 다르게 하면 밀집 시 구분되지 않는다
- 모든 픽업에 1px 검정 외곽선을 적용해야 다수가 밀집한 상태에서도 개수를 파악할 수 있다
- 바닥 색과 충돌하는 색 계열은 제외한다. 어두운 잔디 배경이므로 초록 계열 픽업을 제외하고 파랑·보라·자홍 계열을 사용했다
- 크기가 큰 드랍(골드 더미)은 요소마다 어두운 후광을 먼저 깔고 그 위에 배치한다. 겹친 부분이 한 덩어리로 뭉치지 않는다
- 한 종류를 3~4장 제작해 무작위로 섞어 배치하면 반복 패턴이 드러나지 않는다(잔디 4종)
- 원형으로 배치해야 하는 타일(돌담)은 위쪽을 밝게, 아래쪽을 어둡게 그려 방향에 관계없이 사용할 수 있게 한다. 회전이 필요 없어 배치 코드가 단순해진다
- 가장자리를 디더 알파로 처리한 오버레이(마모 띠)는 바닥 위에 배치하는 것만으로 자연스럽게 섞이므로, 전용 전이 타일을 제작할 필요가 없다

### 주의 사항

- PPU를 카테고리마다 다르게 지정하면 픽셀 밀도가 어긋난다. 바닥은 32 PPU, 캐릭터·적은 50 PPU이므로 바닥 픽셀이 1.56배 굵게 보인다. 현재는 의도적으로 유지하고 있으나, 밀도를 맞추려면 바닥을 50 PPU로 올려야 하고 이 경우 돌담 개수와 문양 크기 계산이 전부 변경된다. 카테고리 작업을 시작하기 전에 PPU를 먼저 결정한다
- 전체 화면 스트레치 패널에 불투명 프레임을 적용하면 게임 화면 전체가 가려진다. `LevelUpPanel`·`ResultPanel`·`ShopPanel`은 앵커가 (0,0)~(1,1)이므로 프레임이 아니라 반투명 스크림(검정 a=0.6~0.8)을 사용해야 한다. 프레임은 크기가 정해진 박스(카드, 리스트 배경)에만 적용한다
- 9-slice 이미지는 `m_Type: 1`(Sliced)로 변경해야 보더가 적용된다. 스프라이트만 교체하면 Simple로 남아 이미지 전체가 늘어난다
- 스프라이트를 적용할 때 `m_Color`를 흰색으로 되돌린다. 플레이스홀더 단계의 틴트 색이 남아 있으면 곱연산되어 의도하지 않은 색이 된다
- 바닥 타일맵은 벽 바깥으로 화면 반폭 이상 확장해야 한다. 카메라가 Ortho 6이라 좌우 10.6유닛을 표시하므로, 벽에 붙으면 그 바깥이 검게 보인다(현재 벽 바깥 16유닛까지 배치)

- PixelLab 생성물은 제3자 에셋 라이선스 이슈가 없으나, [PixelLab ToS](https://pixellab.ai/termsofservice) 상 상업적 이용(포트폴리오 공개 포함) 조건은 사전에 확인한다
- 외부 에셋(무료 에셋 스토어 등)을 사용하지 않으므로 제3자 라이선스 검토 항목은 없다
