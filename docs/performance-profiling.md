# Swarm 성능 측정

[README](../README.md)에 실은 수치의 측정 조건, 도구, 한계를 정리합니다. 아래 수치는 **2026-09-06 기록**이며, 문서 수정 과정에서 새로 측정한 결과가 아닙니다.

> Windows Development Build에서 적 약 400마리 조건의 평균 프레임 시간은 1.41 ms, 평균 GC 할당은 3 B/frame입니다. 전체 18회차에서 GC 수집은 0회로 기록됐습니다. Android 실기기와 보스·다중 장판 최악 조건은 미측정입니다.

## 1. 측정 결과

### 환경과 집계

Unity 6000.4.3f1 / Windows 11 / Development Build / Mono / 1920×1080 Fullscreen / Ultra / vSync off / Ryzen 5 5600 + RTX 4060 Ti.

각 열은 10초 측정 창 3회에서 얻은 **지표별 중앙값**입니다. 한 회차를 대표로 선택한 표가 아닙니다. 적 수는 매 프레임의 `ActiveEnemyCount`를 평균하고 소수점을 버린 회차 값의 중앙값이므로, 측정 내내 같은 수였다는 뜻은 아닙니다. README의 목표 400마리 조건은 아래 399마리 행에 해당합니다.

`평균 ms`는 `Time.unscaledDeltaTime` 누적값을 프레임 수로 나눈 값이며, CPU나 GPU의 특정 작업 시간은 아닙니다. `최저 FPS` 열도 **회차별 최저 FPS의 중앙값**으로, 3회 전체에서 가장 느린 프레임을 나타내지 않습니다. GC B/frame과 SetPass는 회차 평균의 중앙값을 정수로 표시한 값입니다.

| 측정 적 수 | 평균 ms | 평균 FPS | 회차 최저 FPS의 중앙값 | 평균 GC B/frame | SetPass |
| --- | ---: | ---: | ---: | ---: | ---: |
| 149 | 0.84 | 1,187.9 | 292.8 | 1 | 19 |
| 399 | 1.41 | 711.4 | 65.3 | 3 | 25 |
| 699 | 2.88 | 347.6 | 65.2 | 6 | 71 |
| 1,099 | 6.30 | 158.7 | 61.5 | 12 | 78 |
| 1,599 | 11.76 | 85.1 | 41.3 | 19 | 80 |
| 2,199 | 39.86 | 25.1 | 17.4 | 50 | 77 |

당시 원본 리포트 위치: `%USERPROFILE%\AppData\LocalLow\DefaultCompany\Swarm\PerfReports\perf_20260906_154746.md`.
2026-09-18 문서 검토에서 이 원본의 환경·요약표·18회차 기록을 직접 대조했습니다. 원본의 `targetFrameRate`는 -1, `fixedDeltaTime`은 0.02초이며, GC 계측은 `ProfilerRecorder`의 `GC Allocated In Frame`입니다. 원본은 저장소에 포함되어 있지 않습니다.

대조 자료는 [README](../README.md), 로컬 `포트폴리오_박재현.pdf` 2쪽, 위 빌드 리포트, 프로젝트 루트의 `PerfReports/`에 있는 에디터 리포트 5개, 아래 Profiler 이미지와 현재 코드입니다. **기존 기록과 구현을 확인한 것이며 새 성능 측정은 하지 않았습니다.** 원본에 자동 생성된 병목·GC·60 FPS 한계 판정은 측정값과 구분해 해석합니다.

### 목표 400마리 구간의 회차 기록

포트폴리오 2쪽에 기재된 2026-09-06 측정값을 함께 보존합니다. 각 회차는 안정화 3초 후 10초 측정이며, 측정 중 무기 구성을 고정하고 디버그 오버레이를 껐습니다.

| 회차 | 평균 프레임 시간 | 평균 GC Alloc/frame |
| --- | ---: | ---: |
| 1 | 1.41 ms | 3 B |
| 2 | 1.40 ms | 3 B |
| 3 | 1.71 ms | 4 B |
| 중앙값 | 1.41 ms | 3 B |

포트폴리오의 회차 기록은 빌드 원본과 일치합니다. 세 회차의 실측 적 수는 모두 399이며, 최저 FPS는 각각 **65.3 / 141.1 / 50.1**입니다. 따라서 요약표의 65.3 FPS로 모든 프레임이 60 FPS 이상이었다고 말할 수 없습니다.

400은 측정 목표치이자 `Game` 씬의 일반 스폰 상한입니다. [EnemySpawner](../Assets/_Project/Scripts/Spawner/EnemySpawner.cs)의 웨이브와 프로브의 보충 스폰은 `ignoreCap: true`를 사용하므로 전체 개체 수의 절대 상한은 아닙니다.

### 수치가 보여주는 범위

- **할당과 수집을 구분합니다.** GC 수집 0회는 할당이 없었다는 뜻이 아닙니다. 요약표의 1~50 B/frame을 0 B로 바꾸어 표현하지 않습니다.
- **Profiler의 0 B는 캡처 범위에 한정합니다.** 특정 프레임의 게임플레이 경로에서 할당이 없었어도, 스킬 발동·UI 갱신·풀 확장이 포함된 모든 프레임을 검증한 것은 아닙니다.
- **1.41 ms는 데스크톱의 평균값입니다.** 평균이 60 FPS 예산보다 작아도 최악 프레임, 모바일 성능, WebGL 성능을 보장하지 않습니다.
- **측정 조건에 공백이 있습니다.** 무기 구성은 측정 중 고정했지만 무기별 종류·레벨·진화 상태의 상세 기록은 부족하고, 경험치 구슬 수는 통제하지 않았습니다. 적 수만의 순수한 비용으로 해석하지 않습니다.
- **현재 버전 검증이 필요합니다.** 측정 이후 코드·에셋 변경의 영향은 이 기록에 반영되지 않습니다.

### 물리와 렌더링 관찰

적 수가 늘면서 평균 프레임 시간이 증가했고, 특히 높은 개체 수 구간에서 증가 폭이 커졌습니다. 다수의 동적 Rigidbody2D 접촉과 프레임 내 물리 스텝 수 증가는 확인할 후보입니다. 정확한 병목 비율은 CPU Profiler의 시간 측정으로 판단해야 하며, GC 할당량만으로 스크립트 비용을 판단하지 않습니다.

프로브는 평균 프레임 시간이 `fixedDeltaTime`(20 ms)을 넘으면 비교 주의 구간으로 표시하고 GC 적합에서 제외합니다. **20 ms 초과 자체가 Maximum Allowed Timestep 클램프를 증명하지는 않습니다.** 프레임 내 물리 스텝 수와 누적 지연을 함께 확인해야 합니다. 2,199마리 행도 실제 부하 관찰값으로 남기되, 단순 선형 보간으로 60 FPS 한계를 확정하지 않습니다.

SetPass 중앙값은 빌드 Ultra에서 19~80, 에디터 Very Low의 두 번째 측정에서 11~17이었습니다. 실행 환경과 품질이 모두 달라 이 차이를 품질 설정만의 효과로 해석하지 않습니다. SetPass 수만으로 렌더링 병목 여부를 확정하지 않습니다.

## 2. 적용한 변경

- **[탐색 버퍼 재사용](../Assets/_Project/Scripts/Weapon/EnemyTargeting.cs):** `OverlapCircleAll` 기반 탐색을 적 레이어 필터와 재사용 `List`를 받는 경로로 전환했습니다. 리스트 용량 확장 시 할당 가능성은 남습니다.
- **[오브젝트 풀링](../Assets/_Project/Scripts/Weapon/ObjectPool.cs):** 적·투사체·이펙트·픽업을 재사용합니다. 풀 확장과 초기 생성 비용은 별도로 확인해야 합니다.
- **스폰 위치 반영:** Rigidbody2D가 있는 경우 `position`에 직접 반영해 스폰마다 전체 `Physics2D.SyncTransforms()`를 호출하던 경로를 줄였습니다. 콜라이더만 있는 경우에는 전체 동기화가 남아 있습니다.
- **계측 경로 정리:** 스폰 보충에 쓰던 `MethodInfo.Invoke`를 델리게이트로 바꾸고, 측정 창에서는 `DebugStatsOverlay`를 비활성화했습니다.

현재 코드에서 확인한 구현입니다. 반복 할당과 불필요한 작업을 줄이는 목적이지만, 동일 조건의 변경 전후 측정이 없으므로 각 변경의 개선율을 산출하지 않습니다. 에디터와 빌드의 차이도 코드 최적화 효과로 표현하지 않습니다.

## 3. 측정 도구와 재현 절차

도구: [`DebugPerfProbe.cs`](../Assets/_Project/Scripts/Debug/DebugPerfProbe.cs). `UNITY_EDITOR || DEVELOPMENT_BUILD`에서만 포함되며, 활성 `EnemySpawner`가 있는 씬에 자동 설치됩니다. 아래 절차는 현재 구현 기준이며, 당시 측정 빌드의 커밋은 원본에 기록되어 있지 않습니다.

목표 적 수까지 채운 뒤 3초 안정화, 10초 측정을 수행합니다. 스윕은 `{150, 400, 700, 1100, 1600, 2200}` 목표별 3회입니다. 충원·감소 대기 시간에 따라 전체 소요 시간은 달라집니다.

| 입력 | 동작 |
| --- | --- |
| F3 | 목표 적 150 단발 측정 |
| F4 | 목표 적 400 단발 측정 |
| F5 | 적 수를 보충하거나 일반 스폰을 억제하지 않고 현재 상태 측정 |
| F6 | 전자동 스윕 시작 / 중단 |

**F3~F5는 `[PERF]` 콘솔 로그만 남깁니다.** F6 스윕은 완료한 회차마다 Markdown 파일을 저장하며, 중단하면 완료분까지 보존합니다. 파일 위치는 에디터에서 `<프로젝트>/PerfReports/`, 빌드에서 `persistentDataPath/PerfReports/`입니다.

### 실행 전

1. Windows Build Profile에서 **Development Build**를 켭니다. Deep Profiling과 Script Debugging은 수치 측정 시 끄고, Profiler 연결 여부도 기록합니다.
2. 해상도·창 모드·품질·vSync·`targetFrameRate`·`fixedDeltaTime`을 고정합니다. 원본과 비교하려면 위 환경을 맞춥니다. 창 모드로 새로 측정할 경우 원본의 Fullscreen과 구분합니다.
3. `Title`에서 캐릭터를 선택하고 게임을 시작합니다. 캐릭터, 무기별 레벨·진화 상태, 품질 설정, 커밋을 리포트와 함께 기록합니다.
4. 필요한 스킬·이펙트를 한 번씩 실행해 초기 생성 비용을 확인합니다. 워밍업 회차와 본 측정 회차를 구분하고, 제외한 회차를 기록합니다.
5. 카드 창을 닫고 `timeScale = 1`을 확인합니다. F1 배속으로 적을 채우지 않습니다.
6. 비교 실행 간 경험치 구슬 등 픽업 수를 맞추거나 그 수를 기록합니다. 프로브는 픽업 수를 자동 통제하지 않습니다.

### 프로브의 통제 범위

- F3·F4·F6은 일반 스폰 간격을 늘려 억제하고 부족한 적을 보충합니다. 충원은 프레임당 최대 25마리, 안정화·측정 중 보충은 최대 8마리이며 **측정 중 보충 비용도 포함**됩니다.
- 초과 개체는 강제로 제거하지 않고 처치를 기다립니다. 충원·감소가 각각 30초 안에 끝나지 않으면 현재 개체 수로 진행하므로 목표치 도달이 보장되지는 않습니다.
- 현재 `EnemySpawner`의 웨이브·보스 시간 진행은 멈추지 않습니다. 낮은 목표치에서 시작하거나 긴 스윕을 실행할 때 이들 조건도 기록해야 합니다.
- 플레이어 무적을 갱신하고 레벨업 필요 경험치를 높입니다. 바인딩 실패 경고를 확인하고, `timeScale`이 1이 아니면 측정을 보류한 뒤 복귀 시 해당 회차를 다시 시작합니다.
- 측정 창에서 `DebugStatsOverlay`를 비활성화합니다. 무기 구성과 픽업 수는 자동으로 설정하거나 통제하지 않습니다.

GC는 `ProfilerRecorder.LastValue`의 누적값을 프레임 수로 나눕니다. 카운터가 유효하지 않으면 `GC.GetTotalMemory(false)`의 시작·종료 차이를 쓰지만, 이는 관리 힙 크기의 변화에 대한 추정이며 총 할당량과 같지 않습니다. GC 수집 열은 `GC.CollectionCount(0)`의 측정 창 전후 차이입니다. 델리게이트 바인딩 실패 시에는 `MethodInfo.Invoke`로 돌아가므로 새 측정에서는 경고 로그도 보존해야 합니다.

### 보스·다중 장판 조건 — 미측정

`TestStage`에서 진화 무기를 준비하고 F2로 보스를 소환한 뒤, 패턴 실행 중 F4 또는 F5로 측정하는 시나리오가 남아 있습니다. `TestStage`는 현재 일반 빌드 씬 목록에서 비활성 상태이며, 훈련 더미와 별도로 생성한 보스는 `ActiveEnemyCount`에 포함되지 않습니다. 별도 테스트 빌드에서 보스·더미·장판 수도 기록해야 합니다.

출시 구성 확인은 `Game`에서 가능한 무기 조합과 보스 패턴을 준비해 별도로 수행합니다. 장판 수·픽업 수·보스 시전 상태를 함께 기록합니다.

## 4. GC 검증 범위와 후속 확인

### Profiler 캡처

![Unity Profiler GC Alloc 캡처](media/img-02-profiler.png)

이미지의 Profiler 계층에는 `PlayerLoop` 368 B가 `GUIUtility.BeginGUI` 아래에, `EditorLoop` 296 B가 PackageManager·Rendering·Wwise Editor 분기에 표시됩니다. 이는 캡처된 프레임과 표시 범위의 관찰입니다. 이 이미지에는 `DebugStatsOverlay.OnGUI` 호출이 직접 나타나지 않아 368 B 전부를 해당 컴포넌트에 귀속할 수 없습니다.

이미지에 덧붙인 “게임 코드의 몫은 0 B”, “빌드에서는 368 B도 사라진다”는 설명은 캡처만으로 입증되지 않습니다. 본문에서는 이미지의 설명과 확인 가능한 계층 값을 구분하며, 전체 게임플레이가 무할당이라고 결론 내리지 않습니다.

프로브의 에디터 전체 수치 약 9,000 B와 위 샘플 합계 사이에는 차이가 있습니다. 스레드·측정 시점·집계 범위를 맞춰 조사하기 전에는 그 차이 전부를 특정 원인으로 확정하지 않습니다. 적 수에 비례하지 않는 할당도 게임 코드에서 생길 수 있습니다.

### 후보별 상태

| 경로 | 확인 상태 / 다음 검증 |
| --- | --- |

| `RollCooldownUI.Update` | 쿨다운 표시 중 `ToString()` 사용을 코드에서 확인. 해당 스킬을 실행하며 할당 측정 필요 |

| 보스 패턴 | 시나리오 미측정. 등장·시전·종료와 풀 초기 확장 구간 확인 |
| 탐색 버퍼·오브젝트 풀 | 충분한 용량에서의 재사용과 최초 용량 확장을 구분해 측정 |

현재 프로브의 `NegligibleBytesPerFrame = 256`은 GC 자동 판정 문구를 선택하는 프로젝트 기준입니다. 이보다 작다는 사실이 측정 노이즈 또는 무할당의 증거는 아닙니다. 프로브가 출력하는 “사실상 0” 또는 “게임플레이가 아니다”라는 자동 판정을 검증 결과로 옮기지 않습니다. 낮은 전체 평균이나 적 수와의 상관관계만으로 개별 할당 경로를 제외할 수 없습니다.

### 프레임 변동

149마리 구간의 최저 FPS는 회차별 60.9 / 323.1 / 292.8로 변동했고 GC 수집은 0회였습니다. 원인을 드라이버·풀 확장 등으로 확정할 수 없으므로 해당 프레임의 추적이 필요합니다.

에디터 첫 측정(`perf_20260906_141927.md`)의 15회차 기록에서는 GC 수집이 있었던 5건의 최저 FPS가 37.1~58.7, 없었던 10건은 60.8~196.5였습니다. 연관성은 관찰됐지만 집계값만으로 GC 단독 비용이나 인과관계를 확정하지 않습니다. 평균·최저 FPS와 함께 프레임 시간 분포와 느린 프레임의 CPU/GPU 기록을 추가해야 합니다.

## 5. 플랫폼과 남은 검증

| 항목 | 현재 상태 |
| --- | --- |
| Windows / Mono | 2026-09-06 표의 조건에서 측정 |
| Android / IL2CPP | 실기기 미측정. 프레임 시간과 GC 할당 모두 재검증 필요 |
| WebGL | [빌드 문서](webgl-build.md)에 실행 확인 기록은 있으나 이 문서의 성능 측정 대상은 아님 |
| 보스 + 다중 장판 | 미측정 |
| 장시간 플레이·픽업 누적 | 개체 수 통제와 반복 측정 필요 |
| 현재 코드 버전 | 당시 구성과 구분한 재측정 필요 |

풀링과 버퍼 재사용은 플랫폼을 옮겨도 유지할 설계입니다. 그러나 런타임·엔진·실행 경로가 달라질 수 있으므로 데스크톱의 GC B/frame이나 프레임 시간을 Android에 그대로 적용하지 않습니다.

모바일 측정을 위해서는 F3~F6 대신 실행할 화면 입력, 측정 기기에서의 리포트 회수, IL2CPP에서 프로브의 델리게이트 바인딩 동작 확인이 필요합니다. 해상도·품질·목표 프레임·발열 상태도 기록합니다.

## 부록. 에디터 측정 기록

아래 수치는 로컬 `PerfReports/` 원본과 대조했습니다. 이 폴더는 Git 추적 대상에서 제외되어 있으며 에디터 수치와 Development Build 수치는 서로 다른 실행 환경입니다.

### A.1 첫 측정 — 1182×640, Very Low

원본: `perf_20260906_141927.md`.

| 적 수 | 150 | 255 | 400 | 578 | 701 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 평균 ms | 1.92 | 2.33 | 3.05 | 4.07 | 4.91 |
| GC B/frame | 9,953 | 9,980 | 10,042 | 10,083 | 10,087 |

적 수 증가에 비해 전체 할당량의 변화가 작아, 고정적으로 발생하는 비용을 조사하는 계기가 됐습니다. 이 관계만으로 할당의 출처를 확정하지는 않습니다.

### A.2 두 번째 측정 — 1920×1080, Very Low

원본: `perf_20260906_145545.md`.

| 적 수 | 149 | 399 | 698 | 1,098 | 1,597 | 2,200 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 평균 ms | 2.16 | 3.90 | 6.94 | 12.93 | 33.24 | 341.07 |
| GC B/frame | 8,965 | 9,014 | 9,094 | 9,130 | 9,489 | 11,348 |

높은 부하 구간에서 물리 스텝 수가 달라질 가능성을 고려해, 프로브는 20 ms 초과 구간을 GC 적합에서 제외하도록 했습니다. 제외는 비교 조건을 위한 판단이며 해당 구간의 부하를 없었던 것으로 취급하는 것은 아닙니다.

### A.3 제외한 실행

`perf_20260906_152219.md`는 목표 1,100에 **713 / 930 / 872**, 목표 1,600에 **818 / 747 / 694**로 개체 수가 미달해 대표 표에서 제외했습니다(회차 순서). Profiler 연결 여부는 이 리포트에 기록되어 있지 않아 원인으로 단정하지 않습니다.

`perf_20260906_145226.md`는 18회 중 9회, `perf_20260906_162524.md`는 18회 중 1회만 완료한 중단 기록입니다. 완주한 3회 반복 스윕과 구분하며 대표 표에는 사용하지 않았습니다.

### A.4 계측 도구 수정 기록

| 문제 | 대응 |
